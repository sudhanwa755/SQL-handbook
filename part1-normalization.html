Database Normalization

Normalization is the process of organizing a database to eliminate redundancy and data anomalies. You will learn to identify whether a table is in 1NF, 2NF, or 3NF — and exactly how to fix it.

⏱ ~20 min read
🎯 Beginner
📋 5 sections
0

Why Normalize a Database?

Without normalization, databases suffer from three classic anomalies:

✏️
Update Anomaly
Same data stored in multiple rows. Updating one row leaves others stale — causing inconsistency.
➕
Insertion Anomaly
Cannot add new data without inserting unrelated or fake data to fill required columns.
🗑️
Deletion Anomaly
Deleting one record accidentally destroys other important related data.
Key Rule

Each Normal Form (NF) builds on top of the previous one. A table in 3NF is also in 2NF and 1NF. You cannot skip a form.

1.1

First Normal Form (1NF)

A table is in 1NF if:

  • Every column contains atomic (indivisible) values — no lists, no sets.
  • Every column contains values of a single type.
  • Each column has a unique name.
  • The order of rows does not matter.

Table That Violates 1NF

Here is a STUDENT_COURSES table. The Courses column stores multiple values — this breaks 1NF.

Table: STUDENT_COURSES (BAD — Violates 1NF)
StudentIDStudentNameCourses
101AliceMath, Science, English
102BobMath, History
103CarolEnglish

The Courses column has multiple values. This makes querying, filtering, and joining impossible cleanly.

Converting to 1NF

Split the multi-valued column into separate rows, one course per row:

Table: STUDENT_COURSES (FIXED — In 1NF)
StudentIDStudentNameCourse
101AliceMath
101AliceScience
101AliceEnglish
102BobMath
102BobHistory
103CarolEnglish
Key Points — 1NF
  • No repeating groups or arrays in any column.
  • Each cell must hold exactly ONE value.
  • The primary key can be composite (StudentID + Course) if needed.
⚠️ Mistakes to Avoid
  • Storing comma-separated lists like "Math,Science" in one cell — this breaks 1NF.
  • Using columns like Course1, Course2, Course3 — this is a repeating group and also violates 1NF.
1.2

Second Normal Form (2NF)

A table is in 2NF if:

  • It is already in 1NF.
  • Every non-key column is fully functionally dependent on the entire primary key — not just part of it.
📘 Note

2NF only applies when the primary key is composite (two or more columns). If the primary key is a single column, then 2NF is automatically satisfied once 1NF is achieved.

Table That Violates 2NF

The table below has a composite key: (StudentID, CourseID).
StudentName depends only on StudentID — not on CourseID. This is a partial dependency → violates 2NF.

Table: ENROLLMENT (BAD — Violates 2NF)
StudentID CourseID StudentName CourseName Grade
101C01AliceMathA
101C02AliceScienceB
102C01BobMathC

Notice Alice is repeated — that's the update anomaly. Changing Alice's name needs to update every row.

Converting to 2NF — Split into 3 tables

Table: STUDENTS
StudentID StudentName
101Alice
102Bob
Table: COURSES
CourseID CourseName
C01Math
C02Science
Table: ENROLLMENT (Grade only — depends on both keys)
StudentID CourseID Grade
101C01A
101C02B
102C01C
Key Points — 2NF
  • Look for partial dependencies: can a non-key column be determined by just PART of the composite key?
  • If yes — move that column to a new table where the partial key becomes the primary key.
  • Only columns that depend on the FULL composite key stay in the original table.
⚠️ Mistakes to Avoid
  • Thinking 2NF applies to tables with a single-column primary key — it doesn't matter then.
  • Confusing partial dependency with transitive dependency (that's 3NF).
1.3

Third Normal Form (3NF)

A table is in 3NF if:

  • It is already in 2NF.
  • No non-key column is transitively dependent on the primary key.
📘 Transitive Dependency Explained

If A → B and B → C, then A → C transitively.
If A is the primary key and C depends on B (not directly on A), that's a transitive dependency — it violates 3NF.

Table That Violates 3NF

Table: EMPLOYEES (BAD — Violates 3NF)
EmpID EmpNameDeptIDDeptName DeptCity
E01AliceD10EngineeringMumbai
E02BobD10EngineeringMumbai
E03CarolD20MarketingDelhi

Here: EmpID → DeptID and DeptID → DeptName, DeptCity.
So EmpID → DeptName is transitive. DeptName and DeptCity do not directly depend on EmpID.

Converting to 3NF — Split into 2 tables

Table: EMPLOYEES (3NF )
EmpID EmpNameDeptID
E01AliceD10
E02BobD10
E03CarolD20
Table: DEPARTMENTS (3NF )
DeptID DeptNameDeptCity
D10EngineeringMumbai
D20MarketingDelhi
Key Points — 3NF
  • Every non-key column must depend ONLY on the primary key — "the key, the whole key, and nothing but the key."
  • If column C depends on column B, and B is not a key — move B and C to a new table.
  • 3NF eliminates most data redundancy issues in practice.
⚠️ Mistakes to Avoid
  • Confusing transitive dependency with partial dependency — they are different problems.
  • Forgetting to also remove the transitively-dependent columns from the original table.
1.4

How to Identify Which NF a Table Is In

Use this checklist in order:

1
Check 1NF: Does any column store multiple values in a single cell? If YES → table is NOT even in 1NF. Fix it first.
2
Check 2NF: Is the primary key composite? If YES → do any non-key columns depend on only PART of that composite key? If YES → table is in 1NF but NOT 2NF.
3
Check 3NF: Does any non-key column depend on another non-key column? If YES → table is in 2NF but NOT 3NF.
4
If all checks pass → the table is in 3NF .

Summary Comparison

Normal FormWhat It EliminatesRule
1NF Multi-valued cells, repeating groups All values must be atomic
2NF Partial dependencies Non-key columns depend on full composite key
3NF Transitive dependencies Non-key columns depend ONLY on the primary key
