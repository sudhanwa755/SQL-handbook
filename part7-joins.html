7.1a

How a JOIN Actually Works — Row by Row

Seeing the syntax is one thing. Understanding how SQL processes it prevents almost every join mistake. Think of it as SQL picking up each row from the left table and checking every row in the right table against the ON condition.

🧠 Mental Model: The Matching Game

SQL goes through the left table one row at a time. For each row, it checks every row in the right table to see if the ON condition is satisfied. What happens when a match is found — or not — depends on the join type (INNER, LEFT, RIGHT, FULL).

Concept — How SQL Processes INNER JOIN Step by Step
Step 1: Take first row from EMPLOYEES (left table)
        → Alice, DeptID = D10

Step 2: Go through every row in DEPARTMENTS (right table)
        D10 = IT      ← ON condition: D10 = D10? ✓ MATCH
        D20 = HR      ← ON condition: D10 = D20? ✗ no match
        D30 = Finance ← ON condition: D10 = D30? ✗ no match
        D40 = Marketing ← D10 = D40? ✗ no match

Step 3: INNER JOIN → keep only the matched combination
        Result row added: Alice | IT | 85000

Step 4: Move to next EMPLOYEES row (Bob, DeptID = D20)
        ... repeat steps 1–3 for every employee ...

Step 5: Grace (DeptID = NULL) finds no match
        → NULL never equals anything (not even NULL)
        → INNER JOIN discards Grace
        → LEFT JOIN would KEEP Grace with NULL for dept columns

🔑 Does the Order in the ON Clause Matter?

This is one of the most common points of confusion. These two queries look different — are they?

SQL — Version A: e on left of equals
SELECT e.EmpID, e.EmpName, d.DeptName, e.Salary
FROM       EMPLOYEES   e
INNER JOIN DEPARTMENTS d
    ON  e.DeptID = d.DeptID;
SQL — Version B: d on left of equals
SELECT e.EmpID, e.EmpName, d.DeptName, e.Salary
FROM       EMPLOYEES   e
INNER JOIN DEPARTMENTS d
    ON  d.DeptID = e.DeptID;
✅ Both versions produce IDENTICAL results

Why? Because equality (=) is symmetric. Just like in mathematics:

A = B  is identical to  B = A
e.DeptID = d.DeptID  is identical to  d.DeptID = e.DeptID

Swapping the sides of the = sign does NOT change which rows match. It is purely a matter of personal style.

⚠️ But THIS Is Different — Changing the COLUMN

Swapping sides of = is safe. Using a different column entirely is a completely different story:

SQL — Correct vs Wrong ON Condition
-- ✅ Correct: comparing DeptID columns — related values that link the tables
INNER JOIN DEPARTMENTS d
    ON e.DeptID = d.DeptID

-- ❌ Wrong: comparing EmpID to DeptID — unrelated columns!
-- EmpID values: E01, E02...E07  vs  DeptID values: D10, D20, D30, D40
-- These values NEVER match → zero rows returned (or worse: wrong rows!)
INNER JOIN DEPARTMENTS d
    ON e.EmpID = d.DeptID  -- ← logically meaningless!
⚠️ The Golden Rule of ON Conditions

Swapping sides of =: e.DeptID = d.DeptID vs d.DeptID = e.DeptID → ✓ Identical result
Swapping the column used: e.DeptID vs e.EmpID → ✗ Completely different (wrong) result

📊 When One Row Produces Multiple Output Rows

A very important concept beginners miss: one left-table row can produce multiple output rows if the right table has multiple matching rows. This is correct behavior, not a bug.

1-to-Many Example: IT dept (D10) has 2 projects → each IT employee appears twice
RelationshipDescriptionOutput Rows
1-to-1One employee → one dept1 row per employee
1-to-manyOne dept → many projects (D10 → P01, P04)Each IT employee appears TWICE
Many-to-1Many employees → one deptNormal — one row per employee
Many-to-many3 IT employees × 2 IT projects6 rows (3 × 2)
📘 Why Alice Appears Twice in the 3-Table JOIN (§7.7)

IT has two projects (Website Redesign and AI Dashboard). Each combination of Employee + Project forms one output row. Alice (IT) + 2 projects = 2 rows. This is expected and correct.

LEFT JOIN (LEFT OUTER JOIN)

What it returns: All rows from the left table, plus matching rows from the right table. Where there's no match, right table columns are NULL.

SQL — LEFT JOIN
-- All employees, even those without a department

7.4a

ON vs WHERE — The Most Critical Outer Join Trap

This single misunderstanding causes countless incorrect SQL queries. With outer joins, WHERE and ON are NOT interchangeable. Moving a filter from ON to WHERE can silently destroy the purpose of a LEFT JOIN.

ClauseWhen appliedEffect on LEFT / RIGHT / FULL JOIN
ONDuring the join — defines matching rulesUnmatched outer rows still appear (with NULLs for right-table columns)
WHEREAfter the join — filters the combined resultRemoves rows with NULL right columns → effectively converts to INNER JOIN!

Side-by-Side Comparison

SQL — Filter in ON: All employees, dept shown only for D10
SELECT e.EmpName, d.DeptName
FROM      EMPLOYEES   e
LEFT JOIN DEPARTMENTS d
    ON  e.DeptID = d.DeptID
    AND d.DeptID = 'D10';  -- ← filter is part of ON
Result: All 7 employees — only D10 employees get a DeptName
EmpNameDeptNameNote
AliceITD10 match ✓
BobNULLD20 — no D10 match, still shown
CarolITD10 match ✓
DavidNULLD30 — still shown
EvaNULLD20 — still shown
FrankNULLD30 — still shown
GraceNULLNULL DeptID — still shown
SQL — Filter in WHERE: Looks similar — VERY different result!
SELECT e.EmpName, d.DeptName
FROM      EMPLOYEES   e
LEFT JOIN DEPARTMENTS d
    ON  e.DeptID = d.DeptID
WHERE d.DeptID = 'D10';  -- ← filter moved to WHERE
Result: Only 2 rows — the LEFT JOIN silently became an INNER JOIN!
EmpNameDeptName
AliceIT
CarolIT
⚠️ Why Did That Happen?

The LEFT JOIN produces all 7 rows first — 6 with dept data, 1 (Grace) with NULLs. Then WHERE d.DeptID = 'D10' runs on this full result. It removes every row where d.DeptID is not 'D10' — including all the rows where d.DeptID IS NULL. Result: only the 2 IT employees survive.

Classic interview trap: "Write a LEFT JOIN that filters by department." Putting the department filter in WHERE instead of ON accidentally produces an INNER JOIN result.

ON vs WHERE — The Rules
  • INNER JOIN: ON and WHERE are equivalent — there are no outer rows to lose.
  • LEFT/RIGHT/FULL JOIN + right-table filter: Put filter in ON (using AND) to preserve outer rows with NULLs.
  • Use WHERE after outer JOIN when you intentionally want to eliminate unmatched rows — knowing it converts to inner-join behavior.
  • Memory trick: "WHERE kills NULLs. ON preserves them."
7.5

CROSS JOIN — Cartesian Product

What it returns: Every row from the left table paired with every row from the right table. M × N rows total. No join condition needed.

When to use: Generate all combinations (e.g., product + size + color, days of week + shifts).

SQL — CROSS JOIN
-- Generate all dept + project combinations (4 × 4 = 16 rows)
SELECT
    d.DeptName,
    p.ProjectName
FROM       DEPARTMENTS d
CROSS JOIN PROJECTS    p;
⚠️ Warning

On large tables, CROSS JOIN creates enormous result sets. 1000 × 1000 = 1,000,000 rows. Always use intentionally.

7.6

SELF JOIN — Joining a Table to Itself

When to use: When a table has a relationship with itself — for example, employees have a ManagerID that refers to another EmpID in the same table.

SQL — SELF JOIN (Employee-Manager)
-- List each employee with their manager's name
-- Use TWO aliases for the SAME table
SELECT
    emp.EmpID,
    emp.EmpName                            AS EmployeeName,
    mgr.EmpName                            AS ManagerName
FROM      EMPLOYEES emp
LEFT JOIN EMPLOYEES mgr  ON  emp.ManagerID = mgr.EmpID;
-- LEFT JOIN ensures Carol, Eva, Frank (no manager) are still shown

Self Join Key Points
  • Always use table aliases to distinguish the two copies of the same table.
  • Use LEFT JOIN if some rows might not have a matching self-reference (e.g., top-level managers).
  • Common use cases: employee–manager, category–subcategory, city–distance matrix.
7.6a

Self Join — "Same Table, Two Roles" (Deep Dive)

The Self Join confuses almost every beginner. Let's destroy that confusion completely.

🧠 The Core Idea in One Sentence

A Self Join is NOT a special keyword. It is just a regular JOIN (INNER, LEFT, or RIGHT) where both sides of the join refer to the same physical table — each given a different alias so SQL can tell them apart.

Why Join a Table to Itself?

Some tables store relationships within their own rows. The classic example: an EMPLOYEES table where the ManagerID column stores the EmpID of the manager — who is also an employee in the same table.

Concept — Same Table, Two Roles
FROM      EMPLOYEES emp   ← the "employee copy"  (Role 1)
LEFT JOIN EMPLOYEES mgr   ← the "manager copy"   (Role 2)
    ON  emp.ManagerID = mgr.EmpID

Both emp and mgr point to the SAME physical table.
SQL treats them as two separate virtual copies.

Translation of the ON condition:
"Find me a row in the manager copy (mgr)
 whose EmpID matches this employee's ManagerID."

For Alice (emp row):
  emp.ManagerID = E03
  Scan mgr for mgr.EmpID = E03 → that's Carol
  Match! → Output row: Alice | Carol

For Carol (emp row):
  emp.ManagerID = NULL
  NULL matches nothing
  No match → LEFT JOIN keeps Carol with NULL Manager
💡 Why Aliases Are REQUIRED (Not Just Helpful)

Without two distinct aliases, SQL cannot tell which copy of EmpName you mean — the employee's or the manager's. Both columns have the exact same name.

-- ❌ Ambiguous — won't work or gives wrong results:
SELECT EmpName, EmpName        -- Which EmpName?
FROM EMPLOYEES
JOIN EMPLOYEES ON ManagerID = EmpID;  -- Which EmpID?

-- ✅ Clear with meaningful aliases:
SELECT emp.EmpName AS Employee,
       mgr.EmpName AS Manager
FROM EMPLOYEES emp
LEFT JOIN EMPLOYEES mgr ON emp.ManagerID = mgr.EmpID;

Self Join vs Normal Join — Key Differences

ConceptNormal JOINSelf JOIN
Tables involvedTwo different tablesSame table, used twice with aliases
AliasesOptional — for readabilityEssential — without them, queries are ambiguous
Join keywordINNER JOIN, LEFT JOIN, etc.Same keywords — there is no SELF JOIN keyword
ON conditionLinks columns from different tablesLinks two columns within the same table (e.g. ManagerID → EmpID)
When to use LEFT vs INNERDepends on requirementsLEFT JOIN: include rows with no self-reference (top-level managers, NULL ManagerID)

Other Real-World Self Join Use Cases

  • Category → Parent Category: A categories table where each category has a ParentCategoryID pointing to another row in the same table.
  • Employee → Mentor: Same employee table — MentorID references another EmpID.
  • Friend → Friend: A social network table linking UserID pairs in the same users table.
  • City → City (Distances): A distances table where both FromCityID and ToCityID reference the same cities table.
Self Join Memory Tricks
  • "Same table, two roles" — give each role a meaningful alias (emp/mgr, child/parent, etc.).
  • SELF JOIN is not a keyword. Write LEFT JOIN EMPLOYEES mgr, never SELF JOIN EMPLOYEES.
  • Use LEFT JOIN when some rows have no self-reference (you still want to see them with NULL for the other role).
  • Use INNER JOIN when you only want rows that have a valid self-reference.

Joining 3+ Tables in One Query

You can chain as many joins as you need. Each join adds another table to the result.

SQL — 3-Table JOIN
-- Employees + their Department + Department's Projects
SELECT
    e.EmpName,
    d.DeptName,
    p.ProjectName,
    p.Budget
FROM       EMPLOYEES   e
INNER JOIN DEPARTMENTS d  ON  e.DeptID   = d.DeptID
INNER JOIN PROJECTS    p  ON  d.DeptID   = p.DeptID
ORDER BY   d.DeptName, e.EmpName;

7.7a

Common JOIN Mistakes — Troubleshooting Guide

These are the most frequent mistakes beginners make with JOINs. Each shows the wrong approach, explains why it fails, and provides the correct fix.

Mistake 1 — Wrong Column in the ON Clause

SQL — Wrong Column
-- ❌ Wrong: EmpID compared to DeptID — completely unrelated values
INNER JOIN DEPARTMENTS d ON e.EmpID = d.DeptID
-- EmpID values: E01..E07 vs DeptID values: D10..D40 → no rows returned!

-- ✅ Correct: link the column that actually connects the tables
INNER JOIN DEPARTMENTS d ON e.DeptID = d.DeptID
-- Memory trick: follow the foreign key → primary key relationship

Mistake 2 — WHERE Instead of ON with Outer Joins

SQL — WHERE Kills the Outer Join Effect
-- ❌ Wrong: right-table filter in WHERE eliminates outer rows
FROM EMPLOYEES e
LEFT JOIN DEPARTMENTS d ON e.DeptID = d.DeptID
WHERE d.DeptName = 'IT';  -- Removes all non-IT including NULL rows!

-- ✅ Correct: use AND in ON to keep outer rows
LEFT JOIN DEPARTMENTS d
    ON e.DeptID = d.DeptID
    AND d.DeptName = 'IT';  -- Non-IT employees kept with NULL DeptName

Mistake 3 — No Aliases in Self Join

SQL — Ambiguous Self Join
-- ❌ Wrong: SQL cannot tell which copy's column is which
SELECT EmpName, EmpName  -- Ambiguous!
FROM EMPLOYEES
JOIN EMPLOYEES ON ManagerID = EmpID;  -- Which EmpID?

-- ✅ Correct: give each role a meaningful alias
SELECT emp.EmpName AS Employee, mgr.EmpName AS Manager
FROM EMPLOYEES emp
LEFT JOIN EMPLOYEES mgr ON emp.ManagerID = mgr.EmpID;

Mistake 4 — Accidental Cartesian Product (Missing ON)

SQL — Forgotten ON Clause
-- ❌ Wrong: old comma-syntax with no condition → Cartesian product
-- 7 employees × 4 departments = 28 nonsense rows!
SELECT e.EmpName, d.DeptName
FROM EMPLOYEES e, DEPARTMENTS d;  -- no join condition!

-- ✅ Correct: always use explicit JOIN ... ON
FROM EMPLOYEES e
INNER JOIN DEPARTMENTS d ON e.DeptID = d.DeptID;

Mistake 5 — Surprised by Duplicate Rows (This Is Correct!)

SQL — 1-to-Many Produces Multiple Rows
-- "Why does Alice appear twice?"
SELECT e.EmpName, p.ProjectName
FROM EMPLOYEES e
INNER JOIN PROJECTS p ON e.DeptID = p.DeptID;
-- Alice (IT) + Website Redesign → row 1  ✓ correct
-- Alice (IT) + AI Dashboard    → row 2  ✓ correct (NOT a bug!)
-- IT has 2 projects → each IT employee gets one row per project
-- If you only want each employee once, rethink: which project?
JOIN Mistakes Quick Reference
  • Wrong ON column: Link foreign key → primary key. Check what values are actually in each column.
  • WHERE on outer join: Right-table column filters in WHERE silently convert LEFT JOIN to INNER JOIN.
  • Self join aliases: Without two distinct aliases, queries are ambiguous or produce wrong results.
  • Missing ON: Two tables listed without an ON condition = full Cartesian product (M × N rows).
  • Duplicate rows: 1-to-many relationships multiply rows — expected behavior, not a bug.

JOIN Decision Guide + SQL Execution Order

Which JOIN Should I Use?

You want...UseMemory Trick
Only rows matching in BOTH tablesINNER JOIN"Only mutual friends"
All left rows + matching rightLEFT JOIN"Keep everyone from the left class"
All right rows + matching leftRIGHT JOIN"Keep everyone from the right class"
All rows from both sidesFULL OUTER JOIN"Nobody gets left out"
Every combination (M × N rows)CROSS JOIN"Everyone pairs with everyone"
Row related to another in same tableSelf JOIN (INNER or LEFT)"Same table, two roles"

SQL Logical Execution Order

SQL doesn't process clauses in the order you write them. Understanding the logical order explains many seemingly mysterious behaviors.

Concept — SQL Logical Processing Order
1. FROM         → identify source tables
2. JOIN / ON    → combine tables based on the join condition
3. WHERE        → filter individual rows from the combined result
4. GROUP BY     → group the filtered rows
5. HAVING       → filter the groups (use aggregate functions here)
6. SELECT       → compute output columns and expressions
7. DISTINCT     → remove duplicate output rows (if used)
8. ORDER BY     → sort the final result
9. LIMIT/OFFSET → limit how many rows are returned

─────────────────────────────────────────────────────────
This is a LEARNING MODEL of logical order.
The actual database engine may physically optimize differently.
─────────────────────────────────────────────────────────

Why this order matters:
• You cannot use a SELECT alias in a WHERE clause
  → WHERE runs BEFORE SELECT computes aliases
• Aggregate functions go in HAVING, not WHERE
  → WHERE runs BEFORE GROUP BY creates groups
• Moving a filter from ON to WHERE changes outer join behavior
  → WHERE runs AFTER the JOIN is complete
💡 Three Rules That Fall Out of the Execution Order
  • Can't use SELECT alias in WHERE: WHERE runs before SELECT — the alias doesn't exist yet.
  • Aggregates in HAVING, not WHERE: Aggregates summarize groups — groups don't exist until after GROUP BY.
  • ON before WHERE: The join happens first; WHERE filters the already-joined rows.

Join Summary
  • INNER JOIN: Only matching rows from both sides.
  • LEFT JOIN: All left rows + matching right rows (NULLs for non-matches).
  • RIGHT JOIN: All right rows + matching left rows.
  • FULL OUTER JOIN: All rows from both sides.
  • CROSS JOIN: Every combination of rows (M × N).
  • SELF JOIN: Table joined to itself using aliases.
