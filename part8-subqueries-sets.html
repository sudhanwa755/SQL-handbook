Subqueries & Advanced

A subquery is a query nested inside another query. It lets you use the results of one query as a condition or value in another. Master all types — from simple scalar subqueries to complex correlated ones with EXISTS.

8.0

What Is a Subquery?

A subquery (also called an inner query or nested query) is a SELECT statement inside another SQL statement. The outer query is called the main query.

  • Subqueries are always enclosed in parentheses ( ).
  • The inner query executes first, its result is passed to the outer query.
  • Subqueries can appear in the WHERE, SELECT, FROM, and HAVING clauses.
8.0a

How a Subquery Executes — Visual Step-by-Step

The hardest part about subqueries for beginners is understanding which query runs when. The answer is surprisingly simple:

🧠 Core Rule: Inner Query Runs First

SQL always executes the innermost subquery first. Its result becomes a value (or list of values) that the outer query uses. Think of it like evaluating math: (2 + 3) × 4 — you always solve the parentheses first.

Concept — Step-by-Step Execution Trace
Original query:
SELECT EmpName, Salary FROM EMPLOYEES WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEES);

───────────────────────────────────────────────────────────
Step 1: SQL sees the inner subquery in parentheses.
        It runs FIRST:
        SELECT AVG(Salary) FROM EMPLOYEES
        → Result: 76714.28  (one value)
───────────────────────────────────────────────────────────
Step 2: SQL replaces the subquery with its result.
        The outer query becomes effectively:
        SELECT EmpName, Salary FROM EMPLOYEES WHERE Salary > 76714.28
───────────────────────────────────────────────────────────
Step 3: SQL runs the outer query normally.
        → Returns Alice (85000), Carol (92000), Frank (95000)
───────────────────────────────────────────────────────────

The subquery didn't know or care about the outer query.
It just ran and handed back one number. Simple.

💡 Reading a Subquery — Work from the Inside Out

When reading or writing a subquery, always start with the innermost parentheses first:

  1. What does the inner query compute? (e.g., "the average salary")
  2. What does the outer query do with that result? (e.g., "find employees earning more than that")
  3. Read it in plain English: "Find employees earning more than the average salary."
8.1

Scalar Subquery — Returns ONE Value

When to use: When you need to compare a column against a single computed value, like the overall average salary.

SQL — Scalar Subquery in WHERE
-- Find employees earning more than the AVERAGE salary
SELECT EmpName, Dept, Salary
FROM   EMPLOYEES
WHERE  Salary > (
    SELECT AVG(Salary)
    FROM   EMPLOYEES
);

-- The inner query returns: 76714.28  (average)
-- The outer query then runs: WHERE Salary > 76714.28

⚠️ Mistakes to Avoid
  • A scalar subquery must return exactly one row, one column. If it returns multiple rows, you'll get an error.
  • If the subquery might return NULL, handle it with NVL/COALESCE.
8.2

Multi-Row Subquery — Returns Multiple Values

When a subquery returns more than one row, you must use special operators: IN, ANY, or ALL.

Using IN

SQL — Multi-row Subquery with IN
-- Find employees who are managers (appear in ManagerID column)
SELECT EmpID, EmpName, Dept
FROM   EMPLOYEES
WHERE  EmpID IN (
    SELECT DISTINCT ManagerID
    FROM   EMPLOYEES
    WHERE  ManagerID IS NOT NULL
);
-- Inner query returns: (E03, E05, E06)
-- Outer query finds employees whose EmpID is in that list
Result: Employees who are managers

Using ANY and ALL

SQL — ANY and ALL
-- ANY: salary greater than AT LEAST ONE HR salary
SELECT EmpName, Salary
FROM   EMPLOYEES
WHERE  Salary > ANY (
    SELECT Salary FROM EMPLOYEES WHERE Dept = 'HR'
);
-- HR salaries: 55000, 62000
-- ANY: salary > 55000 (the smallest)

FROM   EMPLOYEES

8.3

Correlated Subquery

A correlated subquery references a column from the outer query. It executes once for every row in the outer query (row-by-row execution).

An uncorrelated (non-correlated) subquery is completely independent — it runs once and its result is reused.

SQL — Correlated Subquery
-- Find employees earning MORE than the average of THEIR OWN department
SELECT
    e1.EmpName,
    e1.Dept,
    e1.Salary
FROM   EMPLOYEES e1
WHERE  e1.Salary > (
    SELECT AVG(e2.Salary)
    FROM   EMPLOYEES e2
    WHERE  e2.Dept = e1.Dept  -- ← references outer query's Dept!
);

-- For each outer row (e1), the inner query filters by e1.Dept:
-- IT rows: inner query calculates IT avg = (85000+92000+70000)/3 = 82333
-- HR rows: inner query calculates HR avg = (55000+62000)/2 = 58500
-- Finance: inner query calculates Finance avg = (78000+95000)/2 = 86500
Result: Employees earning above their dept's average
EmpNameDeptSalaryDept Avg
CarolIT9200082333 (IT Avg)
EvaHR6200058500 (HR Avg)
FrankFinance9500086500 (Finance Avg)
Correlated vs Uncorrelated
  • Uncorrelated: Inner query is independent. Runs ONCE. Faster.
  • Correlated: Inner query references outer query column. Runs for EVERY outer row. Slower but more powerful.
  • You can often rewrite a correlated subquery as a JOIN for better performance.
8.3a

Correlated Subquery — Row-by-Row Execution Trace

The correlated subquery is the hardest concept to visualize. Let's trace it completely, one outer row at a time.

🧠 The Key Difference vs Uncorrelated

Uncorrelated: inner query runs once → result reused for all outer rows.
Correlated: inner query runs once per outer row → it uses a value from that specific outer row.

Concept — Row-by-Row Trace for the Correlated Query
Query: "Find employees earning MORE than their dept's average"

Outer row 1: Alice (IT, 85000)
  → Inner query runs: SELECT AVG(Salary) FROM EMPLOYEES WHERE Dept = 'IT'
  → IT avg = (85000 + 92000 + 70000) / 3 = 82333
  → 85000 > 82333? YES ✓ → Alice included

Outer row 2: Bob (HR, 55000)
  → Inner query runs: SELECT AVG(Salary) FROM EMPLOYEES WHERE Dept = 'HR'
  → HR avg = (55000 + 62000) / 2 = 58500
  → 55000 > 58500? NO ✗ → Bob excluded

Outer row 3: Carol (IT, 92000)
  → Inner query runs with Dept = 'IT' again: avg = 82333
  → 92000 > 82333? YES ✓ → Carol included

Outer row 4: David (Finance, 78000)
  → Inner query runs: SELECT AVG(Salary) FROM EMPLOYEES WHERE Dept = 'Finance'
  → Finance avg = (78000 + 95000) / 2 = 86500
  → 78000 > 86500? NO ✗ → David excluded

Outer row 5: Eva (HR, 62000)
  → HR avg = 58500
  → 62000 > 58500? YES ✓ → Eva included

Outer row 6: Frank (Finance, 95000)
  → Finance avg = 86500
  → 95000 > 86500? YES ✓ → Frank included

Outer row 7: Grace (IT, 70000)
  → IT avg = 82333
  → 70000 > 82333? NO ✗ → Grace excluded

Final result: Alice, Carol, Eva, Frank
⚠️ Performance Note

The inner query ran 7 times (once per outer row). With 1 million employees, that's 1 million inner executions. This is why correlated subqueries can be slow on large tables.

For production systems, you'd often rewrite this as a JOIN with a derived table or use a window function (AVG(Salary) OVER (PARTITION BY Dept)).

💡 How to Spot a Correlated Subquery

Look for a column reference in the inner query's WHERE clause that uses the outer query's table alias (e.g., e1.Dept inside the inner WHERE e2.Dept = e1.Dept). If the inner query references the outer table → it's correlated.

8.4

EXISTS and NOT EXISTS

When to use: To check whether a subquery returns any rows at all. More efficient than IN for large datasets because it stops as soon as one match is found.

EXISTS returns TRUE if the subquery returns at least one row. It ignores the actual data — only tests for existence.

SQL — EXISTS
-- Find employees who HAVE appeared as a ManagerID (i.e., they manage someone)
SELECT EmpID, EmpName, Dept
FROM   EMPLOYEES e1
WHERE  EXISTS (
    SELECT 1   -- SELECT 1 is a convention (doesn't matter what you select)
    FROM   EMPLOYEES e2
    WHERE  e2.ManagerID = e1.EmpID
);

-- NOT EXISTS: employees who manage NO ONE
SELECT EmpID, EmpName, Dept
FROM   EMPLOYEES e1
WHERE  NOT EXISTS (
    SELECT 1
    FROM   EMPLOYEES e2
    WHERE  e2.ManagerID = e1.EmpID
);

8.4a

The NOT IN + NULL Trap — Critical Gotcha

This is one of the most dangerous silent bugs in SQL. NOT IN with a list that contains NULL always returns zero rows — and SQL gives you no warning.

SQL — The NOT IN NULL Bug
-- "Find employees who are NOT managers"
-- This looks correct but has a hidden NULL problem:
SELECT EmpName
FROM   EMPLOYEES
WHERE  EmpID NOT IN (
    SELECT ManagerID  -- ← ManagerID column contains NULLs!
    FROM   EMPLOYEES
);
-- Inner query returns: (E03, E05, E06, NULL, NULL, NULL)
-- NOT IN with a NULL in the list:
-- SQL checks: EmpID != E03 AND EmpID != E05 AND EmpID != E06 AND EmpID != NULL
-- NULL != NULL is UNKNOWN (not FALSE, not TRUE)
-- UNKNOWN in an AND chain = entire condition = UNKNOWN
-- UNKNOWN is treated like FALSE → row excluded
-- Result: ZERO rows returned! Every employee is excluded!
NOT IN with NULLs — returns 0 rows (wrong!)
EmpName
No rows returned ← silent bug!
SQL — Fix 1: Filter NULLs before NOT IN
SELECT EmpName
FROM   EMPLOYEES
WHERE  EmpID NOT IN (
    SELECT ManagerID
    FROM   EMPLOYEES
    WHERE  ManagerID IS NOT NULL  -- ← exclude NULLs from the list
);
-- Now inner query returns: (E03, E05, E06) — no NULLs
-- NOT IN works correctly again
SQL — Fix 2: Use NOT EXISTS (always safe with NULLs)
SELECT e1.EmpName
FROM   EMPLOYEES e1
WHERE  NOT EXISTS (
    SELECT 1
    FROM   EMPLOYEES e2
    WHERE  e2.ManagerID = e1.EmpID
);
-- NOT EXISTS checks row-by-row, not against a list with NULLs
-- NULL ManagerIDs never match e1.EmpID → does not affect the result
-- Correctly returns: Alice, Bob, David, Grace
NOT IN vs NOT EXISTS — Rules
  • NOT IN (subquery that might have NULLs): Dangerous — returns 0 rows silently. Always add WHERE col IS NOT NULL inside the subquery.
  • NOT EXISTS: Always safe — NULL-proof by design. Preferred when the subquery column could be NULL.
  • Memory trick: "NOT IN hates NULLs. NOT EXISTS ignores them."
8.5

Subquery in FROM Clause (Inline View / Derived Table)

A subquery in the FROM clause creates a temporary table that the outer query can use. You must give it an alias.

SQL — Subquery in FROM
-- First compute dept averages, then filter depts with avg > 70000
SELECT
    dept_summary.Dept,
    dept_summary.AvgSalary
FROM (
    -- Inner query: compute averages per department
    SELECT
        Dept,
        ROUND(AVG(Salary), 2) AS AvgSalary,
        COUNT(*)                AS EmpCount
    FROM     EMPLOYEES
    GROUP BY Dept
) dept_summary   -- Alias is mandatory
WHERE dept_summary.AvgSalary > 70000
ORDER BY dept_summary.AvgSalary DESC;

8.6

Nested Subqueries

Subqueries can be nested inside other subqueries. This allows very complex conditions to be expressed cleanly.

SQL — Nested (Multi-level) Subquery
-- Find employees in the department with the HIGHEST total salary bill
SELECT EmpName, Dept, Salary
FROM   EMPLOYEES
WHERE  Dept = (
    -- Level 2: find which dept has the max total salary
    SELECT Dept
    FROM   EMPLOYEES
    GROUP BY Dept
    HAVING SUM(Salary) = (
        -- Level 3: what is the maximum total salary across all depts?
        SELECT MAX(DeptTotal)
        FROM (
            SELECT SUM(Salary) AS DeptTotal
            FROM EMPLOYEES
            GROUP BY Dept
        ) totals
    )
);
Result: Employees in IT (highest total salary dept = 247000)

Subquery in HAVING

SQL — Subquery in HAVING
-- Find departments whose avg salary > overall avg salary
SELECT
    Dept,
    ROUND(AVG(Salary), 2) AS DeptAvg
FROM     EMPLOYEES
GROUP BY Dept
HAVING   AVG(Salary) > (
    SELECT AVG(Salary) FROM EMPLOYEES
);
Result: Depts with avg salary above overall avg (76714)
DeptDeptAvg
Finance86500.00
IT82333.33
Subquery Summary
  • Scalar: Returns one value. Use with =, >, <.
  • Multi-row: Returns many values. Use with IN, ANY, ALL.
  • Correlated: References outer query. Runs per outer row.
  • Uncorrelated: Independent. Runs once.
  • EXISTS: Tests if any row exists. Fast; handles NULL correctly.
  • Inline View: Subquery in FROM. Must have alias.
  • In HAVING: Filter groups using aggregate results from another query.
⚠️ Mistakes to Avoid
  • Using = with a multi-row subquery — this throws an error. Use IN instead.
  • Using NOT IN when the subquery might return NULLs — NOT IN (1, 2, NULL) always returns no rows! Use NOT EXISTS instead.
  • Forgetting to alias subqueries in the FROM clause.
  • Deeply nested subqueries are hard to read — consider rewriting as JOINs or Common Table Expressions (CTEs) for clarity.
8.8

Subquery vs JOIN — When to Use Which

Both subqueries and JOINs can often solve the same problem. Knowing when to use each makes your SQL cleaner and faster.

SituationUseWhy
Need a single derived value for comparison (e.g., average)Scalar SubqueryClean, readable
Check if ANY related row existsEXISTS or INSubquery is cleaner; EXISTS is faster
Check if NO related row existsNOT EXISTSSafer than NOT IN (NULL-proof)
Need columns from BOTH tables in resultJOINSubqueries can't easily return columns from two tables
Aggregation over groups, then filter groupsDerived table in FROM or CTECan't use WHERE on aggregate aliases
Compare each row to its own group's aggregateCorrelated SubqueryBut consider window functions for large tables

Same Result, Two Approaches

SQL — Subquery Version: Employees who are managers
SELECT EmpName
FROM   EMPLOYEES
WHERE  EmpID IN (
    SELECT DISTINCT ManagerID FROM EMPLOYEES WHERE ManagerID IS NOT NULL
);
SQL — JOIN Version: Same result using a self-join
SELECT DISTINCT mgr.EmpName
FROM      EMPLOYEES emp
INNER JOIN EMPLOYEES mgr
    ON emp.ManagerID = mgr.EmpID;
-- JOIN is more natural here if you also want manager details.
-- Subquery is more natural if you only need a yes/no existence check.

Common Subquery Mistakes — Quick Reference

⚠️ Common Subquery Mistakes
  • = with multi-row subquery: WHERE Salary = (SELECT Salary FROM ...) → error if inner returns multiple rows. Use IN.
  • NOT IN with NULLs: Always add IS NOT NULL inside the subquery, or use NOT EXISTS.
  • Missing alias on FROM subquery: FROM (SELECT ...) — the alias after the closing parenthesis is required.
  • Correlated query on huge tables: If the inner query runs for every outer row, consider rewriting with a JOIN + GROUP BY or a window function.
  • Deeply nested subqueries: Hard to read, hard to debug. Refactor to a CTE (WITH dept_avg AS (SELECT ...)) for clarity.
